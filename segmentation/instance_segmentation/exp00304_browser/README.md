# exp00304: ブラウザで動かす(ONNX Runtime Web の WebGPU・WASM)

## 目的

学習したモデルを、ブラウザの中だけで動かす(サーバーなし)。GitHub Pages のデモのページ(リポジトリ直下の `index.html` と `site/`)に
載せる。動画の入力は YouTube の URL(埋め込み)・手元の動画と画像のファイル・カメラ。

## 使ったもの

| 部分 | 中身 |
|---|---|
| 実行 | onnxruntime-web 1.31.1(jsDelivr から読む)。WebGPU を先に試し、使えなければ WASM(CPU) |
| モデル | exp00301 の `export_onnx.py --webgpu` で書き出した fp32 の ONNX を、exp00302 の `quantize_weights.py` で重みだけ INT8 にしたもの。Hugging Face の [tkyk1234/cv-experiments-models](https://huggingface.co/tkyk1234/cv-experiments-models) の `segmentation/instance_segmentation/` に置き、ページはそこから直接読む |
| ページのコード | `site/app.js`(画面)、`site/lib/runtime.js`・`site/lib/ort_worker.js`(ONNX Runtime Web を Web Worker で動かす)、`site/lib/sources.js`(動画の入手)、`site/tasks/instance_segmentation.js`(前後の処理と描画)、`coi-sw.js`(下の問題 4) |
| 確かめ方 | Windows の Chrome を headless で動かし、ページの自己テスト(URL に `?selftest=画像のパス&backend=webgpu&model=...&onnx=...`)の結果の表示を、Chrome のデバッグの接続(DevTools Protocol)で読む。1 回ごとに制限時間(30〜120 秒)をつけ、止まっても待ち続けないようにした |

## 起きた問題と直し方

| # | 問題 | 原因 | 直し方 |
|---|---|---|---|
| 1 | GitHub のファイルの上限(1 ファイル 100MB)を超える。実験が増えるとリポジトリの容量も足りなくなる | fp32 の ONNX が GTR 系 146MB・YOLO26-seg 系 180MB | 重みを INT8 にして 42MB・46MB(問題 8)。置き場所は Hugging Face のモデルのリポジトリにした(公開のファイルはブラウザから直接読める。Google Drive の公開のリンクはブラウザから読めないという報告が多いので使わない) |
| 2 | モデルの準備や推論の間、ページ全体が固まる | ONNX Runtime Web をページの処理と同じ流れ(メインスレッド)で動かしていた | Web Worker の中で動かす。準備に 120 秒の制限時間をつけ、超えたら Worker を止めて次の実行の場所を試す |
| 3 | YouTube の動画を推論に入れられない | 別のサイトの動画の画素は読めない(ブラウザの決まり)。動画のファイルを取ってくるのは規約上も避ける | 公式の埋め込みで再生し、このタブの画面の取り込み(`getDisplayMedia`)を、埋め込みの場所だけに切り抜く(Region Capture: `CropTarget.fromElement` → `track.cropTo`)。結果は埋め込みに重ねると取り込まれてしまうので、横に並べて描く。PC 版の Chrome・Edge だけで動く |
| 4 | WASM が遅い(1 コマ 2.7 秒、0.4 コマ毎秒) | WASM が 1 つのスレッドで動いていた。複数のスレッドには、ページが cross-origin isolated(COOP・COEP のヘッダー)である必要があるが、GitHub Pages ではヘッダーを足せない | service worker(`coi-sw.js`)で応答にヘッダーを足す(初めて開いたときに 1 回だけ読み込み直す)。COEP は `credentialless` にし、YouTube の iframe も `credentialless` にする。スレッドの数は CPU のコアの数 − 1(最大 8)。8 スレッドで 1 コマ 1.18 秒(YOLO26-seg 系、問題 8 の静的な INT8 のとき) |
| 5 | 再生を止めた・共有を切った後に止まる、最初のコマのまま変わらない、推論のエラーが表示されない | コマの待ち方と、エラーの扱いが足りなかった | `requestVideoFrameCallback` で次のコマを待つ(1 秒で打ち切る)。取り込みの終わり(track の `ended`)で止める。ループの中のエラーを捕まえて状態の欄に出す |
| 6 | WebGPU でモデルの準備が終わらない | 下の「WebGPU で準備が終わらない原因」 | exp00301 の `export_onnx.py --webgpu` で、同じ計算を次元の少ない形に差し替えて書き出す |
| 7 | ONNX を読めない(`optimizer_execution_frame.cc` のエラー) | 書き出した ONNX の重みが別のファイル(`model.onnx.data`)に分かれていた。ブラウザにはグラフのファイルしか渡していない | 重みを含めた 1 つのファイルにする(量子化した ONNX は 1 つのファイルで保存される) |
| 8 | 静的な INT8 が WebGPU で遅い(1 回の推論 GTR 系 4.2 秒・YOLO26-seg 系 2.4 秒) | 静的な量子化は計算も 8 ビットの整数で行うが、その演算(`QuantizeLinear`・`QLinearConv` など)に WebGPU が対応しておらず、その部分が CPU で動く | 重みだけの INT8 にする(下の「モデルの形式」) |
| 9 | GTR 系の予測が正しくない(スコアがほぼ 0) | ブラウザではなく静的な量子化で壊れていた(Python の ONNX Runtime でも同じ)。Gather・GatherElements の量子化が原因(exp00302 の README) | 問題 8 で重みだけの INT8 にしたので、サイトのモデルには当てはまらない。静的な量子化をするときは、この 2 つを fp32 のまま残す |
| 10 | 重みだけ INT8 のモデルで、推論のたびに重みを INT8 から fp32 に戻す計算が走っていた | ONNX Runtime は既定で、量子化したモデルの最適化のために、重みを戻す処理(DequantizeLinear)を定数にまとめずに残す(exp00302 の README の「重みを戻す処理」) | Worker でセッションを作るときに `session.disable_quant_qdq = 1` を渡し、読み込むときに 1 回だけ戻す。精度は変わらない。ネイティブの CPU で −7〜17%、ブラウザの WebGPU で −4%(567 ms と 591 ms。headless で測った値)。ブラウザの WASM(8 スレッド、画面に見えるウィンドウ + 裏のページの動作を抑えない設定、ほかの学習を一時停止して、交互に 2 回ずつ)では修正なし 348・336 ms、修正あり 340・333 ms で −1〜2%(ぶれと同じくらいで、ほぼ効かない。ネイティブと効き方が違う理由は確かめていない) |
| 11 | 普段使いの Chrome で GitHub Pages のデモを WASM で動かすと、YouTube の取り込みで 0.5 fps(1 コマ 1,832 ms)しか出ない | 新しいプロファイルの Chrome・シークレットモードでは同じページが 2.7〜2.8 fps(1 コマ 350〜365 ms)なので、ページやモデルではなく、その Chrome のプロファイルの状態が原因。何が原因かは確かめていない(シークレットモードでは拡張機能が切れ、サイトのデータ(service worker・sessionStorage・キャッシュ)も別になる。1,832 ms は WASM が 1 スレッドのときの見込みに近い) | 遅いときは、シークレットモードか別のプロファイルで開く。画面共有(YouTube の取り込み)そのものの影響は +10 ms 程度(手元の動画のとき 352 ms、取り込みのとき 363 ms) |

途中で間違えたこと: 問題 6 の原因が分かる前に、モデルの形式(静的な INT8 → 重みだけの INT8)を変えて直そうとした。fp32 でも同じように
止まったので、形式は原因ではなかった。原因の演算を 1 つずつ切り分けるまで、直し方を決めないこと。

## WebGPU で準備が終わらない原因

演算 1 つだけの小さい ONNX を作り、1 つずつ WebGPU で試した(Windows の Chrome、GPU のシェーダーの変換は Chrome の既定の DXC と、
古い FXC(`--disable-dawn-features=use_dxc`)の両方)。

| 演算(試した形) | DXC(既定) | FXC |
|---|---|---|
| 行列の掛け算 2 次元 | すぐ終わる | すぐ終わる |
| 行列の掛け算 3 次元(batch のある掛け算) | 1 回目の推論に約 24 秒 | すぐ終わる |
| 行列の掛け算 4 次元(注意の (1, 頭, n, d)) | 終わらない | — |
| 要素ごとの掛け算、5 次元どうしで形が同じ | すぐ終わる | すぐ終わる |
| 要素ごとの掛け算、5 次元で別の形を広げる(broadcast。例 (1, 300, 8, 12, 2) × (12, 1)) | 終わらない | 終わらない |
| 同、4 次元で broadcast | 1 回目の推論に 2.5〜3.7 秒 | 同じくらい |
| 同、3 次元で broadcast、スカラー・1 次元のベクトルとの broadcast | すぐ終わる | すぐ終わる |
| 畳み込み、Linear(3 次元の入力 × 2 次元の重み)、GridSample、並べ替え | すぐ終わる | すぐ終わる |

ONNX Runtime Web の WebGPU は、演算の形(次元の数・広げ方)ごとに GPU のシェーダーを作る。次元の多い行列の掛け算と broadcast は、
そのシェーダーの準備が極端に遅いか、終わらない。モデルの中でこれにあたる場所:

- YOLO26-seg 系: PSA の注意(4 次元の行列の掛け算)
- GTR 系: encoder の AIFI と decoder の自己注意(`nn.MultiheadAttention`。3〜4 次元の行列の掛け算)と、deformable な注意で点の位置を
  計算する部分(5 次元の broadcast)

切り分けの順: モデル全体 → 部品ごと(backbone・encoder・クエリの選び出し・decoder の自己注意・deformable な注意)に切った ONNX →
止まった部品の中の 1 つずつの計算。「GridSample が怪しい」などの見込みは、切り分けると外れていた(GridSample だけの ONNX は
すぐ終わり、止まっていたのはその前の点の位置の計算だった)。

`export_onnx.py --webgpu` は、書き出すときだけ次の forward を差し替える(学習のコードは変えない)。

| 差し替え | 中身 |
|---|---|
| `psa_forward_2d`(YOLO26-seg 系の PSA) | 注意を、頭ごとの 2 次元の行列の掛け算 (hw, d) × (d, hw) に分ける |
| `mha_forward_2d`(`nn.MultiheadAttention`) | 同じく頭ごとの 2 次元に分ける(batch 1・マスクなしの推論のとき) |
| `deform_forward_low_rank`(GTR 系の deformable な注意) | 点の位置を (B·M, 頭·点, 2) の 3 次元で計算してから、grid_sample の形に並べ替える |

| 候補 | 差し替えの前と後の出力の差の最大(PyTorch fp32) | WebGPU(DXC)でのモデルの準備 | 1 回の推論(2 回目) |
|---|---|---|---|
| 自作の GTR 系 + hybrid encoder | クラスの値 4e-6・枠 4e-7・マスク 4e-5(上位 100 個の並びも同じ) | 1.7 秒 | 0.58 秒 |
| 自作の YOLO26-seg 系 | 6e-5 | 2.0 秒 | 0.57 秒 |

(fp32 の 1 つのファイルで試した値。時間は 1 回ずつ測っただけの目安)

## モデルの形式

| 作り方(exp00302) | 8 ビットにするもの | 計算 | WebGPU | WASM(8 スレッド) |
|---|---|---|---|---|
| 静的な量子化(`quantize.py`) | 重みと、計算の途中の値 | 8 ビットの整数で計算する | 整数の計算に WebGPU が対応せず、その部分が CPU で動く(GTR 系 4.2 秒・YOLO26-seg 系 2.4 秒) | 約 1.0 秒 |
| 重みだけ(`quantize_weights.py`) | ファイルの中の重みだけ | fp32 に戻して計算する(戻すのは、ONNX Runtime の設定で読み込むときの 1 回だけにする。問題 10) | GPU だけで動く(GTR 系 0.54 秒・YOLO26-seg 系 0.57 秒) | 0.96〜1.35 秒 |

(1 回の推論の時間。同じ画像で 1 回ずつ測っただけの目安。ファイルの大きさはどちらも 40MB 前後)

重みだけの INT8 は WebGPU でも WASM でも動き、調整の画像も要らないので、サイトはこれ 1 つのファイルにした
(GTR 系 42MB・YOLO26-seg 系 46MB)。ブラウザの出力は、同じ画像の Python の ONNX Runtime の出力とほぼ同じ
(GTR 系の上位の検出: ブラウザ chair 0.50・bottle 0.38)。精度(exp00302。ONNX Runtime の CUDA で測った): test の mask AP は GTR 系 31.91・YOLO26-seg 系 30.73 で、fp32
(31.83・30.71)と変わらない。

## ネイティブの ONNX Runtime と、ブラウザの WASM の時間の差

同じファイル(サイトの GTR 系、重みだけの INT8、問題 10 の設定あり)を、ネイティブの ONNX Runtime の CPU と、ブラウザ(Windows の Chrome、
ONNX Runtime Web 1.31.1)の WASM で比べた。ほかの学習のプロセスを一時停止して CPU を空けた状態で測った。ブラウザは自己テスト
(`?selftest=...&repeat=15&threads=N`)で 15 回続けて推論し、Worker の中の推論そのもの(`session.run`)の時間を見た(出力を JS の配列に
写す時間は 1 ms 未満)。

| 条件 | 1 回ごとの時間 | 中央値 |
|---|---|---|
| ネイティブ、8 スレッド | 134〜160 ms(安定) | 約 140 ms |
| ネイティブ、16 スレッド | — | 129 ms |
| ブラウザ、headless(画面に出さない) | 1,090〜1,460 ms | 1,143〜1,354 ms |
| ブラウザ、画面に見えるウィンドウ | 最初の 5 回は 340〜460 ms、その後 550 ms 前後に遅くなる | 548 ms |
| **ブラウザ、画面に見えるウィンドウ + 裏のページの動作を抑えない設定** | **321〜355 ms(安定)** | **333 ms** |
| 同上、16 スレッド・19 スレッド | — | 339 ms・348 ms |

(どれも WASM は 8 スレッド。抑えない設定は Chrome の `--disable-renderer-backgrounding --disable-background-timer-throttling
--disable-backgrounding-occluded-windows`)

- それまで測っていたブラウザの WASM の 1 秒前後の値は、ほとんどが「見えていないページ」として Chrome(と Windows)に動作を抑えられた分
  だった。headless で測ると、ページが常にその扱いになる
- 画面に見えるウィンドウでも、続けて動かすと遅くなる(340 → 550 ms)。測るためのウィンドウがほかのウィンドウの裏にある・前面にないと、
  同じように抑えられると見ている(確かめていない)。実際に使うときも、デモのタブを前面に出していないと遅くなりうる
- 抑えない状態での、ネイティブとの差は約 2.4 倍(333 ms と 140 ms)。スレッドを 8 より増やしても速くならない。残りの差は WASM そのもの
  (使える SIMD 命令の幅など)と見ている(確かめていない)
- この CPU(Intel Core Ultra 7 265K)は速いコア 8 個と省電力のコア 12 個でできていて、Windows は裏のプロセスを省電力のコアに回すことが
  ある。抑えられたときに遅くなる理由はそれと見ているが、確かめていない
- これからブラウザの時間を測るときは、画面に見えるウィンドウ + 抑えない設定で測る(`cdp_selftest.py` の `CVX_HEADFUL=1` と上の設定)

## 動画のループの段ごとの時間と、WebGPU が使う GPU

実際の推論の繰り返し(`app.js` の `loop`)に、1 コマの時間を段ごとに出す表示を足し、自己テストの動画のモード(`?selftestvideo=...&frames=40`)で、
手元の動画(COCO の画像から作った 1280 × 720・30 fps の動画)を流して測った(40 コマの平均。1 回目は準備を含むので除く)。画面に見える
ウィンドウ + 裏のページの動作を抑えない設定、ほかの学習を一時停止。モデルは今のサイトの GTR 系(重みだけの INT8、問題 10 の設定あり)。

| 実行の場所 | 1 コマ | 取り込み | 前処理 | 推論 | 後処理 | 描画 | 次のコマを待つ |
|---|---|---|---|---|---|---|---|
| WASM(8 スレッド) | 377 ms(2.7 fps) | 0 | 11 | 336 | 1 | 0 | 28 |
| WebGPU(Chrome が選んだ GPU = CPU に入っている Intel Xe-LPG) | 582 ms(1.7 fps) | 0 | 11 | 552 | 1 | 1 | 18 |
| WebGPU(RTX 5090。Chrome の起動の指定 `--force-high-performance-gpu`) | **87 ms(11.5 fps)** | 0 | 11 | **43** | 1 | 0 | 32 |

- ページの JS の処理(前処理・後処理・描画)は合わせて約 12 ms で、ボトルネックではない。1 コマの時間のほとんどは推論
- Chrome の WebGPU は、この PC(CPU に GPU が入っていて、別に RTX 5090 もある)では、CPU に入っている省電力の GPU を使っていた。
  ページから性能の高い GPU を頼んでも(`powerPreference: "high-performance"`、確かめ用の `&gpu=high`)変わらない(556 ms)。Windows では、
  Chrome が使う GPU は OS の設定(設定 → ディスプレイ → グラフィックス で Chrome を「高パフォーマンス」にする)か Chrome の起動の指定で決まる
- RTX 5090 を使うと推論は 556 → 41〜43 ms(約 13 倍速い)。省電力の GPU では WASM(336 ms)より遅いので、既定の「自動」(WebGPU を先に
  使う)では、遅い方が選ばれていた
- 使っている GPU の名前を、実行の場所の表示(例「webgpu(nvidia blackwell)」)に出すようにした
- 「次のコマを待つ」時間(推論の後に、動画の次のコマが来るのを待つ時間)を減らした: 動画のコマが新しく出るたびに番号を記録し、推論の間に
  新しいコマが来ていれば待たずにすぐ次の推論を始める。来ていなければ(推論がコマの間隔より速いとき)次のコマを待ち、同じコマを何度も
  推論しない。WASM・30 fps の動画で、待つ時間 28 → 0 ms、1 コマ 377 → 354 ms(−6%)。WebGPU(RTX 5090、推論 46 ms)・10 fps の動画
  (コマの間隔 100 ms)では、1 コマ 100 ms(待つ時間 41 ms)で、コマの間隔どおりに 1 コマ 1 回だけ推論する

### 軽い構成(exp00105 の HGNetV2-B2 + 軽い後段)

サイトに、exp00105 の HGNetV2-B2 + exp00104 の軽い後段(重みだけ INT8、16.6MB)を足した。同じ条件(画面に見えるウィンドウ、ほかの
学習・評価を一時停止)の WASM(8 スレッド)で測った。

| モデル | 推論だけ(静止画で 15 回の中央値) | 動画のループの 1 コマ(60 コマ) | 段ごと(前処理 / 推論 / 後処理・描画 / 待つ) |
|---|---|---|---|
| R50 の GTR 系(上の表と同じモデル) | 339 ms | 354 ms(2.8 fps。上の「次のコマを待つ」を減らした後の値) | — |
| 軽い構成(HGNetV2-B2) | 125 ms(−63%) | **138 ms(7.2 fps)** | 13 / 124 / 1 / 0 |

- 推論の時間は、ネイティブの ONNX Runtime CPU(4 スレッドで 192 → 70 ms、−64%。exp00301 の README の 5)と同じ割合で縮む
- 裏で CPU を使う処理(精度の評価)を動かしたままでは、1 コマ約 220 ms(4.5 fps)だった
- R50 の動画のループの値は、前に測った値(この回は、R50 の動画の自己テストが 2 回とも読み込みのエラーで止まった)

## WebGPU 用の差し替えと、ファイルを WASM 用・WebGPU 用に分けるか

WebGPU 用の差し替え(上の「WebGPU で準備が終わらない原因」の 3 つ)が CPU で遅くならないか、WASM 用には差し替えのないファイルを使う
(ファイルを 2 つに分ける)と速くなるかを測った。サイトの GTR 系(exp00103 の A の学習済みの重み)を、差し替えの入れ方を変えて書き出し
(`export_onnx.py --webgpu --webgpu-patches ...`)、どれも重みだけの INT8(問題 10 の設定あり)にした。学習が 2 本動いていて CPU が
混んでいる時に、比べる版を交互に測った(値そのものより、版どうしの比が意味を持つ)。

ネイティブの ONNX Runtime の CPU(中央値。括弧は差し替えなしに対する割合):

| 版 | 1 スレッド | 4 スレッド | 8 スレッド |
|---|---|---|---|
| 差し替えなし | 754 ms | 327 ms | 265 ms |
| 注意を頭ごとに分ける(mha)だけ | 751 ms(−0%) | 319 ms(−2%) | 253 ms(−5%) |
| 点の位置を 3 次元で計算する(deform)だけ | 721 ms(−4%) | 303 ms(−7%) | 251 ms(−5%) |
| 両方(今のサイトのファイル) | 767 ms(+2%) | 300 ms(−8%) | 249 ms(−6%) |

ブラウザ(Windows の Chrome、ONNX Runtime Web 1.31.1)の WASM(8 スレッド)。上の節の正しい条件(画面に見えるウィンドウ + 裏のページの

## 残っていること

- CPU(WASM)では 1 コマ約 350〜380 ms(上の「動画のループの段ごとの時間」)。backbone(R50)だけでなく、backbone より後ろの部分も重い
  (GTR 系 + hybrid encoder で約 19 GMACs)。CPU(エッジ機器・ブラウザ)向けの軽い構成は exp00104、軽い backbone は exp00105 で比べる
- **ネイティブの ONNX Runtime と WASM の差(約 2.4 倍)を縮める方法を調べる**(後で行う)。調べる候補:
  - ONNX Runtime Web の新しい版(今は 1.31.1)で、WASM の計算が速くなっているか
  - 静的な INT8(計算も INT8。Gather・GatherElements は fp32 のまま)が、WASM では fp32 の計算より速いか(前に測ったのは、動作を
    抑えられた headless の条件だけ)
  - ONNX Runtime Web のほかの実行の場所(XNNPACK など。使えるかから確かめる)
  - ONNX Runtime 以外の、ブラウザの CPU で動かす仕組み(LiteRT.js の XNNPACK、WebNN の CPU。WebNN は 2026-10 時点で Chrome ではまだ
    フラグの裏)
  - 同じ条件で、ネイティブと WASM の演算ごとの時間(プロファイル)を比べ、どの演算で差が大きいかを見る
