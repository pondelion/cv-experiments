# instance_segmentation: インスタンスセグメンテーションのスクラッチ実装と合成データ

インスタンスセグメンテーション(画像の中の物体を 1 つずつ見分けて、クラスとマスクを出す)のモデルをスクラッチで実装し、
**人手のラベルを使わない合成データだけで学習する**方法を、段階的に検証していく。

最終的な目標は 2 つ。

1. スクラッチ実装のモデルを、最新の論文・公開モデルと同じかそれ以上の精度・速度まで伸ばす
2. 合成データで学習する方法を確立する(インスタンスマスクがあれば検出の枠も作れるので、検出など他のタスクにも使い回せる形にする)

## 方針

- **モデル**: フルスクラッチで実装する。最新の公開実装は、実装の参考にするのと、比較対象としてそのまま動かすのに使う。
  モデルの構成(アーキテクチャ)の比較は、データの比較と並ぶ一番上の観点
- **学習データ**: 基本は合成データ(生成モデルで画像を作り、正解ラベルも自動で用意する)。
  実データ(COCO train の人手ラベル)は、上限の基準と、モデルの構成を論文の値と比べるときにだけ使う。
  正解ラベルは出どころで ① 生成だけ・② 疑似ラベル・③ 組み合わせに分け、混ぜずに比べる([exp00201 の「正解ラベルの作り方の分類」](exp00201_gt_mask_pilot/README.md#正解ラベルの作り方の分類))
- **認識モデル・判定モデル**: ② ③ で、既存のモデル(SAM 3 など)での疑似ラベルと、画像の判定モデル(decision model。選択肢ごとの
  較正された確率を返すモデル)での検品・誤りの原因の分類に使う
- **評価データ**: 公開されている、ラベル付きのベンチマーク。複数のデータセットで評価して、特定のデータセットの見た目に寄っていないかを見る
- **指標**: 精度が第一。推論の速さ(書き出し・量子化・蒸留・ブラウザでの実行)も本格的に検証し、最後に精度と速度のトレードオフの図にする
- **クラス**: まずは Pascal VOC の 20 クラス(COCO の 80 クラスに全部含まれる)。比較の実験の基本は、そのうちの 8 クラス(1 回の学習を
  短くするため。「計画の見直し」の節)。必要になった段階で COCO の 80 クラスに広げる。
  後でクラスを決めないオープンボキャブラリーの実験もするので、データはクラス名を文字列で持ち、語彙を広げて作り直せる形にする

## 比較の軸

| 軸 | 中身の例 | 学習し直し |
|---|---|---|
| モデルの構成 | 1 段・アンカーなし + マスクの原型の係数(YOLACT・YOLO-seg 系)/ 2 段(Mask R-CNN 系)/ 動的な畳み込み(CondInst・SOLOv2 系)/ クエリ方式(Mask2Former・Mask DINO 系)/ 速いクエリ方式(RF-DETR-Seg・LW-DETR 系) | 要る |
| 部品の実装 | backbone・neck・ヘッドごとに、簡略版 → 論文相当 → 別の構成への置き換え。正解の割り当て(IoU の閾値 / 予測の良さで動的に決める / ハンガリアン法)、マスクの損失(BCE・Dice・点を選んで計算する損失) | その部品から後 |
| 外部モデル | backbone の事前学習の重み: なし / ImageNet(ResNet・ConvNeXt)/ 自己教師あり学習(DINOv2・DINOv3)。固定する / 全部学習する / LoRA | 要る |
| 学習データ | 実データ(上限)/ 正解ラベルの作り方(exp00201 の「正解ラベルの作り方の分類」の ①生成だけ・②疑似ラベル・③組み合わせと、その中の方法)、枚数、文章の多様性、生成モデル、方式の混合、少量の実データとの併用 | 要る |
| 学習の仕方 | 学習の長さ、入力の解像度・複数の解像度、データ拡張(大きく拡大縮小・切り貼り)、EMA、損失の重み | 要る |
| 推論の設定 | 入力の解像度、スコアの閾値、重なりの除去(NMS)の有無と閾値、出す数の上限 | 要らない |
| 推論の最適化 | bf16・torch.compile → ONNX Runtime → TensorRT(fp16・INT8)→ 量子化を考えた学習 → 蒸留・枝刈り → ブラウザ(ONNX Runtime Web) | 量子化を考えた学習・蒸留は要る |
| 評価の方法 | mask AP → 境界の正確さ(Boundary AP)・ドメイン違いのデータセット → オープンボキャブラリーの指標(LVIS の珍しいクラスの AP など) | 要らない |

### 進める順番

合成データで学習するには、(1) 合成画像に正解のマスクを自動で付けられること、(2) 学習するモデル(スクラッチ実装)と学習の仕組みがあること、の 2 つが要る。
(1) はこの計画全体で一番の不確かさなので、モデルを作る前に確かめる。(1) と (2) はお互いに依存しない。
正解ラベルの作り方は、まず ① 生成だけ を確かめ、② 疑似ラベル・③ 組み合わせ は ① の後に比較として行う。

| 順 | exp | 何をするか | 前提 | 何がわかれば次に進むか |
|---|---|---|---|---|
| 1 | exp00001 | 評価の基盤・公開モデルの参照点・画像の生成の速さ | - | 評価のセットと評価のコードが正しく動き(公開モデルで公式の値を再現できる)、目標になる公開モデルの精度・速度と、1 枚の画像の生成にかかる時間がわかる |
| 2 | **exp00201** | **① 生成だけ で正解マスクを作る方法(①-a・①-c)の試作と、その質の確認**(学習はしない) | exp00001 | 正解のマスクを作れる割合・速さと、規則の誤差の出方がわかり、exp00202 で学習に使う設定を決められる |
| 3 | **exp00002** | 画像の判定モデル(decision model)での検品の仕組みの確かめ: (1) 生成した単一の物体が指定したクラスか、(2) 背景に学習するクラスの物体が入っていないか。答えのわかる問題で精度・較正・速さを測る | exp00201 | exp00201 で、1 段目の単一の物体の生成で頼んだクラスではない物体(20 クラスのどれでもない「何か」)が描かれること、2 段目の背景の inpainting で背景に学習するクラスの物体が描かれることがわかったため。③ の検品に使うモデルと設定が決まる |
| 4 | exp00101 | スクラッチのモデルの方式の一次比較(COCO の実データで学習) | exp00001 | 学習の仕組みができ、フェーズ B で固定するモデルが決まる。学習の速さから、フェーズ B の枚数・学習の長さを決められる |
| 5 | exp00101〜00108(フェーズ C) | 実データ(8 クラス・2,000 枚)だけで、モデルと学習の仕方を詰めて精度を上げる(下の「計画の見直し」) | 4 | 方式・データ拡張・backbone・学習の仕方の最良の組み合わせが決まり、公開モデルに近い精度になる |
| 6 | exp00202〜00205 | ① 生成だけ の方法で作ったデータで、5 で決めたモデルを学習し、実画像のベンチマークで比べる | 2・5 | ① だけでどこまで届くかがわかる |
| 7 | exp00206〜 | ② 疑似ラベル・③ 組み合わせ(exp00002 の検品を使う)との比較、要因の分析。以降、フェーズ D〜F | 3・6 | 各 exp の表のとおり |

2 と 3 はお互いに独立なので、GPU・メモリがあふれない範囲で並行して進めてよい(遅延を測るものは同時に動かさない)。

### 計画の見直し(exp00101 の最初の結果を受けて)

最初の計画では、exp00101 で方式を一度比べたら、合成データ(フェーズ B)に進み、フェーズ C(モデルの構成)はフェーズ B と交互に
進めるつもりだった。exp00101 の最初の 2 本(Mask2Former 系と RF-DETR-Seg。どちらも backbone は ResNet-50、20 クラス・
coco_train_10pct の 9,528 枚・50 エポック)を回した結果、1 回の学習が長すぎる(20 クラス・9,528 枚で 1 本 2〜3 時間かかり、
比較の実験を何十回も回せない)ことがわかり、順番とデータの設計を見直した。

そこで、

1. **フェーズ C(001xx)を先に、実データだけで進める。** exp00202 の合成データ(20 クラス)の生成は、途中まで作った分を残して止めておく
2. **比較の実験の基本のデータを、8 クラス・学習 2,000 枚にする**([exp00001 の「比較の実験の基本: 8 クラス・学習 2,000 枚」](exp00001_eval_and_baselines/README.md#比較の実験の基本-8-クラス学習-2000-枚)。1 本 30〜40 分の見込み)。
   学習データの量の影響は、データの量だけを変える比較の実験(exp00108)で見る

公式の RF-DETR-Seg・公式の Mask2Former と自作の Mask2Former 系の違いは、exp00101 の README の「方式ごとの対応と違い(公式・自作)」の表に
すべて並べた。同じデータ・クラス・入力・エポック数で、backbone を同じ ResNet-50 にした公式の RF-DETR-Seg は 50 エポックで mask AP 28.8、
自作は 3.6 で、フェーズ C の最初は、この表の違いを 1 つずつ切り分けて自作の精度を公式に近づけることから始める。

exp00101 の最初の 2 本の結果(20 クラス・10%)は、そのまま残す。フェーズ C の進める順番(案): exp00101 の基準を 8 クラス・2,000 枚で
取り直す → exp00107 データ拡張 → exp00102 論文の実装との差 → exp00105 backbone → exp00103 最新の手法 → exp00106 自己教師ありの事前学習 →
exp00108 データの量(実際は exp00101 → exp00102 → exp00103 → exp00104 CPU(エッジ機器・ブラウザ)向けの軽い構成 → exp00105 backbone の順に進めている)。1 本ごとの差が小さい比較では、乱数の種を変えて 2〜3 回回し、ばらつきより大きい差かを確かめる。

### フェーズ C: モデルの構成の比較

学習データは、COCO train の 8 クラス・2,000 枚(`coco_train_cls8_2k`)を基本にし、val は `coco_val_dev_cls8`(最良の重みを選ぶ)、test(最終の精度)は `coco_val_test_cls8`・`voc_val_cls8`。
フェーズ B より先に進める(「計画の見直し」の節)。フェーズ B の最良の合成データでの比較は、フェーズ B の後で必要なものだけ行う。

| exp | 基準 | 変えるもの | 狙い |
|---|---|---|---|
| exp00102 | 00101 の自作の方式 | 公式(論文)の実装との差を埋める。洗い出した差は exp00102 の README(Mask2Former 系の FPN の pixel decoder の実装(論文では FPN でも 41.5 と学習できる)・学習率の変化・初期値、YOLO26-seg 系の最適化・1 回の更新あたりの枚数・損失の重みなど)。多重解像度の deformable な pixel decoder と点を選ぶマスクの損失は exp00101 で済み | 一次比較の差が、方式の差か実装の簡略化の差かを切り分ける |
| exp00103 | 00102 | 最新の手法の比較: 着手時に最新の手法を調べ直し、有望なものをスクラッチ実装して比べる(2026-11 時点の候補: EoMT(ViT だけで完結)、RF-DETR-Seg・ECInsSeg 系(DETR 系の検出 + 軽いマスクのヘッド)、GTR)。古典の Mask R-CNN は比較の参考として 1 本だけ並べる | 最新の手法の良し悪しを、同じデータ・同じ学習の長さで確かめる |
| exp00104 | exp00101〜00103 の方式(backbone は R50 に固定) | CPU(エッジ機器・ブラウザ)向けの軽い構成: これまで精度の高かった方式(GTR 系 + hybrid encoder、YOLO26-seg 系、RF-DETR-Seg 系)の backbone より後の部分を、公式の小さい版(D-FINE・DEIM・YOLO26 の n・s など)の考え方で小さくして比べる。今の構成は backbone より後ろだけで 13〜31 GMACs あり、軽い backbone にしても CPU では速くならない(exp00304・exp00105 の README) | 軽い構成で、どの方式がどこまで精度を保てるか。軽い backbone の比較(exp00105)の土台になる方式と構成を決める |

## 結果のまとめ

> **「GTR 系」という呼び方の注記**: この README と各 exp で「自作の GTR 系」と呼んでいるモデルは、GTR の論文(arXiv 2609.26590)の
> 中心である backbone(ゲート付き線形注意の ViT)を含まない。backbone より後ろ(D-FINE・DEIM 系の decoder と損失、GTR の論文の
> 組み合わせと設定)だけを使い、backbone は timm のもの(R50 など)にしている。exp00103 の A 以降(G0)は encoder も RT-DETR の
> hybrid encoder なので、実態は「RT-DETR / D-FINE 系のインスタンスセグメンテーション」に近い。名前はこれまでの結果との対応のため
> そのまま使う。GTR の backbone そのものは比べない(理由は exp00105 の README の「論文の軽量モデルが使う backbone」)。

各 exp の結果の詳細は、それぞれの README の「結果」に書く。ここには全 exp の主な指標を並べる。
